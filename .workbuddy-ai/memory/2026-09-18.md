# 2026-09-18

## Arreglo: error 42703 `column "DeletedAt" ... does not exist` al guardar/listar clases

**Causa raíz**: desincronización de esquema, no bug de código. La base de datos de desarrollo
tenía aplicada solo `20260909225120_InitialCreate`; la migración
`20260917232218_AddLessonSoftDelete` (añade `Lessons.DeletedAt`) existía en el código pero nunca
se había ejecutado. EF Core genera SQL con `l."DeletedAt"` y PostgreSQL lo rechaza con SQLSTATE
42703. Fallaban tanto el listado (`LessonReader.cs:32`) como el guardado (`LessonService.cs:15`).

**Diagnóstico**: `dotnet ef migrations list --startup-project backend/Api --no-build` mostraba
`20260917232218_AddLessonSoftDelete (Pending)`. El host de design-time necesita la cadena de
conexión; se obtiene de `.tools/local-settings.json` → `ConnectionStrings__Default`.

**Arreglo aplicado** (sin cambios de código):

```
dotnet ef database update --project backend/Infrastructure --startup-project backend/Api --no-build
```

Ejecutó `ALTER TABLE "Lessons" ADD "DeletedAt" timestamp with time zone;`. `/health/ready` pasó de
503 a 200. Verificado el ciclo completo por HTTP: crear clase 201, listar 200, papelera 204,
`state=trash` devuelve `deletedAt`, restaurar 204. Sin pérdida de datos (columna nullable, sin
default).

## Particularidades del entorno (importante para futuras sesiones)

- El `dotnet` del repo (`.tools/dotnet`) tiene SDK **10.0.401**, pero `global.json` exige
  **9.0.318** y solo existe en `C:\Program Files\dotnet`. Usar `dotnet` del PATH, no
  `.tools/dotnet`.
- **`dotnet restore` NO funciona en este entorno de agente** (pero `--no-restore` sí).
  El shell no tiene `APPDATA` ni `PROGRAMDATA` (solo sobreviven `USERPROFILE` y `LOCALAPPDATA`),
  y NuGet los necesita para resolver su carpeta machine-wide:
  `System.ArgumentNullException: Value cannot be null. (Parameter 'path1')` en
  `NuGet.Common.NuGetEnvironment.GetFolderPath` ← `XPlatMachineWideSetting..ctor()`.
  Exportar esas variables desde Git Bash no sirve (el sandbox las filtra antes de lanzar el
  proceso); `cmd /c` está bloqueado por política; PowerShell pierde stdout/stderr del hijo.
  **Solución**: los proyectos ya están restaurados (`obj/project.assets.json` existe y la caché
  `~/.nuget/packages` tiene 505 paquetes), así que basta con:
  `dotnet build Profefacilisimo.slnx --no-restore` y
  `dotnet test Profefacilisimo.slnx --no-restore --no-build`.
  No es un problema del proyecto.
- No hace falta `DOTNET_CLI_HOME` para `dotnet ef`: funciona directamente con `dotnet` del PATH.
- Para comandos `dotnet ef` hay que exportar `ConnectionStrings__Default` y `Jwt__SigningKey`
  desde `.tools/local-settings.json`, más `ASPNETCORE_ENVIRONMENT=Development`.
- Para las pruebas de integración hay que exportar además `TEST_DATABASE_CONNECTION` con la misma
  cadena de conexión.

## Pendiente / opcional (no implementado, requiere decisión del usuario)

El proceso tiene un hueco: las pruebas de integración/E2E usan bases desechables `pf_test_*` /
`pf_e2e_*` y nunca tocan la base de desarrollo, así que una migración sin aplicar en local no se
detecta hasta que falla un endpoint. Opciones propuestas (ninguna implementada):
- Chequeo de CI que falle si `HasPendingModelChanges()` es true.
- Aviso al arrancar la API si `GetPendingMigrationsAsync()` no está vacío.

Descartado explícitamente: migrar automáticamente al arrancar (contradice `docs/phase-1.md:29`).
