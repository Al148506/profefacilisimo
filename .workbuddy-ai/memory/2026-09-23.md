## SPEC 02 simplificada para el MVP (análisis documental, sin código)

Se analizó `specs/02-editor-de-actividades.md` (24 KB) contra el estado real del repo
(SPEC 01 ya implementada y aprobada) y se generó `specs/02-editor-de-actividades-mvp.md`.
El borrador detallado se conserva como referencia de las funcionalidades pospuestas.

**Hallazgos del análisis (importantes para futuras revisiones):**

- **Contradicción documental resuelta**: SPEC 02 presuponía `Lesson.Version`, ETag/`If-Match` y
  412/428, pero SPEC 01 los pospuso explícitamente y adoptó `last write wins` (SPEC 01 §11 ya lo
  dejaba anotado como pendiente de revisar). La versión MVP elimina toda concurrencia optimista.
- **`TransitionAfterMinutes` pospuesto** aunque figuraba como "confirmado por el usuario" en el
  borrador anterior: no es necesario para el flujo de éxito y añadía campo + migración + la regla
  de "la última no cuenta". Añadirlo después es aditivo (columna nullable + recálculo).
- **Drag & drop pospuesto**: los botones Subir/Bajar cubren el criterio de éxito y son accesibles.
- **Consecuencia clave**: sin intervalos y sin versiones, el MVP **no necesita ninguna columna ni
  tabla nueva**. `Activity.EstimatedDuration` (int?) y `Lesson.EstimatedDuration` (int?) ya existen.
  La única migración (`AddCalculatedLessonDuration`) solo cambia `CK_Lesson_Duration` para admitir
  `0` y rellena los totales existentes.
- **`backend/Api/LessonEndpoints.cs` e `ILessonService.cs` no necesitan cambios**: los contratos
  viajan por el binding existente (`SaveLessonRequest`) y la validación vive en `LessonService`.
- El índice único `(LessonId, Order)` no admite colisiones ni transitorias, así que el reordenado
  sigue necesitando las dos fases (posiciones temporales) dentro de la transacción. Se mantiene,
  descrito en 3 viñetas en vez de una sección entera.
- Total = suma de duraciones (sin intervalos) ⇒ **el total no depende del orden**. Sirve como
  caso de prueba verificable y simplifica el dominio.
- `POST /api/lessons` debe crear con total `0`, no `null`; `null` queda reservado a datos
  heredados incompletos.

**Entregable**: documento con la estructura pedida (objetivo, alcance, incluidas, pospuestas,
reglas de negocio, modelo de datos, API, pantallas, archivos, plan) + criterios de aceptación,
decisiones y riesgos. Plan de **10 etapas verificables**, cada una compilando y probable por
separado.

**Estado**: Borrador. Sin cambios de código. Pendiente de revisión del usuario y de ejecutar
`/spec-impl 02-editor-de-actividades-mvp` si se aprueba.

## SPEC 02 MVP — implementación, modo `step`

Spec aprobada (`Estado: Aprobado`). Rama creada: `spec-02-editor-de-actividades-mvp`
(desde `main`, que ya tiene SPEC 01 mergeada vía PR #1). Modo `step`: se para tras cada etapa.

### Etapa 1 — Dominio: edición de una actividad (completada)

- `backend/Domain/Activity.cs`: nuevo `Activity.Update(title, instructions, content, estimatedDuration)`.
  Conserva `Id`, `LessonId` y `Order`; valida TODO antes de asignar nada (sin actualización parcial);
  `Type` se deriva del propio contenido, así que un par tipo/contenido incompatible no puede
  almacenarse. Duración obligatoria mediante la nueva regla.
- `backend/Domain/Lesson.cs`: nueva `Rules.RequiredDuration(int)` (positiva, no nullable) junto a la
  existente `Rules.Duration(int?)` que se mantiene para datos heredados.
- `tests/Domain.Tests/ActivityEditingTests.cs` (nuevo, 12 tests).
- Verificación: `dotnet test tests/Domain.Tests` → **46/46** (34 previos + 12 nuevos).
  `dotnet build backend/Infrastructure` → 0 errores, 0 advertencias.

**Interpretación anotada (duración fraccionaria)**: `EstimatedDuration` es `int` de extremo a extremo
(§6.3), así que 12.5 minutos no tiene representación en la ruta de escritura. Se cubre con una
aserción sobre el tipo del parámetro (`int`) + `JsonSerializer.Deserialize<int>("12.5")` → `JsonException`.
La comprobación HTTP de 400 por duración fraccionaria corresponde a la etapa 5 (integración).

### Etapa 2 — Dominio: conjunto de actividades, orden y total (completada)

- `backend/Domain/Lesson.cs`:
  - Nuevo `ActivityDraft(Guid? Id, string Title, string Instructions, ActivityContent Content, int EstimatedDuration)`.
  - Nuevo `Lesson.ApplyActivities(IReadOnlyList<ActivityDraft>)`: valida **todo el conjunto antes de
    mutar** (Id repetido / ajeno / desconocido → rechaza el guardado completo), actualiza las que
    conservan Id (misma instancia, para el tracking de EF), crea las que no lo tienen, elimina las
    omitidas y asigna `Order` 0..n-1 en el orden del array.
  - **Se elimina el parámetro `estimatedDuration` del constructor**: el total ya no lo aporta el
    llamador. Una clase nueva nace con total 0 (antes `null`).
  - `TotalOf` + `RecalculateDuration`: 0 sin actividades, suma si todas tienen duración, `null` si
    alguna carece de ella. Suma con `checked` → `OverflowException` en vez de truncar.
  - `AddActivity` y `Duplicate` recalculan el total (antes lo arrastraban manualmente).
- `backend/Domain/Activity.cs`: `ValidateEditableData` (validación sin mutación, compartida con
  `Update`) y `SetOrder(int)`.
- `tests/Domain.Tests/LessonTests.cs`: reescritos los tests que fijaban el total manual
  (`NonPositiveDurationIsRejected`, `DuplicatePreservesAllActivityDataWithIndependentIdentities`,
  `EmptyLessonDuplicateRespectsTitleLimit`, `MetadataAcceptsExactLimitsAndSupportedLevels`) y
  añadidos 10 tests nuevos (total 0/30/20/incompleto, orden 0..n-1, Id repetido/ajeno, conjunto
  inválido, desbordamiento, orden independiente del total).
- `tests/Integration.Tests/LessonManagementTests.cs`: ajustados los 3 sitios que pasaban duración al
  constructor y 2 aserciones de total.
- Verificación: `dotnet test tests/Domain.Tests` → **55/55**.

**Observación de secuencia (importante)**: el dominio de la etapa 2 ya produce total `0` para clases
sin actividades, pero `CK_Lesson_Duration` sigue siendo `IS NULL OR > 0`, así que **36 tests de
integración fallan** con `23514: violates check constraint "CK_Lesson_Duration"`. Es exactamente lo
que arregla la migración `AddCalculatedLessonDuration` de la **etapa 3**; la suite vuelve a verde al
aplicarla. La verificación propia de la etapa 2 (`LessonTests`) pasa.

**Nota de diseño**: `Activity.Update` es público y no notifica al agregado, así que editar una
actividad suelta no refresca el total de la clase; el total lo refresca `Lesson.ApplyActivities`.
Es correcto en el flujo real (todo guardado pasa por `ApplyActivities`) pero conviene recordarlo.

### Decisiones de diseño ya tomadas (no reabrir sin motivo)

- El constructor de `Lesson` **no** acepta duración: el total siempre se calcula. Clase nueva = 0.

- El contenido específico se valida pero **no** se recorta (solo título e instrucciones).
- Duración fraccionaria: `int` de extremo a extremo; el 400 HTTP se verificará en la etapa 5.
