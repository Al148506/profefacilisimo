### Siguiente: etapa 5 — escritura (POST/PUT transaccional con el conjunto)

⚠️ **Gotcha de EF Core confirmado con evidencia (bloquea la etapa 5 si se ignora).**
Al añadir actividades nuevas a una clase **ya existente** (estado `Unchanged`), EF **no** las marca
`Added` al descubrirlas por la navegación en `DetectChanges`: como `Activity.Id` es
`ValueGeneratedOnAdd` y la clave ya viene puesta, las marca `Modified` y genera
`UPDATE "Activities" SET ... WHERE "Id" = @p` → 0 filas → `DbUpdateConcurrencyException`.
Medido en el test `ListAndDetailExposeTheCalculatedTotalOrNullWhenIncomplete`:

```
UPDATE "Activities" SET "Content" = @p0, "EstimatedDuration" = @p1, ... WHERE "Id" = @p7   -- ← debería ser INSERT
UPDATE "Lessons" SET "EstimatedDuration" = @p32, "UpdatedAt" = @p33
```

Funciona cuando el padre también es nuevo (`db.Lessons.Add(...)`: el grafo entero entra como `Added`),
por eso `Seed`, `Duplicate` y `PersistenceTests` no lo sufren. El patrón que ya usa el repo para
insertar en una clase existente es añadirlas explícitamente:
`db.Activities.AddRange(first, second)` (ver `DetailsContainOrderedReadonlyActivitiesAndJsonObjectsWithoutOwner`).

**Implicación para la etapa 5**: `LessonService.UpdateAsync` debe marcar como `Added` las actividades
creadas por `Lesson.ApplyActivities`. Dos opciones: (a) capturar los Id existentes antes de aplicar y
hacer `db.Activities.Add` con las que no estaban; (b) cambiar `ApplyActivities` para que devuelva las
creadas (`IReadOnlyList<Activity>`) y hacer `db.Activities.AddRange(...)`. La (b) es más explícita y
evita adivinar; implica tocar la firma ya commiteada de la etapa 2.

## Skill global `/multi-ag-spec` (paralelización de specs entre varios agentes)

Creada la skill de usuario `~/.workbuddy-ai/skills/multi-ag-spec/` a petición del usuario. Toma una
spec como argumento y devuelve una versión reorganizada para trabajo paralelo multiagente.

Estructura: `SKILL.md` (7 fases), `references/output-template.md` (esqueleto del documento de
salida), `references/parallelization-playbook.md` (taxonomía de conflictos, catálogo de puntos
calientes del repo, patrones de carril, plantilla de briefing por agente), y dos scripts:
`scripts/spec_inventory.py` (inventario determinista de archivos + puntos calientes, solo lectura) y
`scripts/worktrees.sh` (planifica/ejecuta worktrees; dry-run por defecto).

Decisiones de diseño relevantes:

- Se escribe un **fichero nuevo** (`specs/<basename>-parallel.md`), nunca se sobrescribe la spec
  original. La línea de estado se copia literal para que `/spec-impl` siga aceptando el fichero.
- Los criterios de aceptación se copian **verbatim**: paralelizar cambia el *quién/cuándo*, no el
  *qué*. Si un criterio no se puede cumplir, la skill se detiene y lo reporta.
- Partición por **propiedad de archivos**, no por tema. Recurso de escritor único: carpeta de
  migraciones, `AppDbContextModelSnapshot.cs`, `AppDbContext.cs`.
- La Fase 0 (contrato congelado) es lo que compra el paralelismo real entre backend y frontend.
- Política de pruebas: durante las fases paralelas solo contrato + regresión crítica + compilar.
  Cobertura, refactor de suites y E2E completo van a la fase de integración.
- Aviso de aislamiento: los subagentes de una misma sesión comparten `cwd`; el plan asume **una
  sesión por worktree**. Sin eso el plan no es ejecutable.

  clase».

## SPEC 03 — Plan paralelo multiagente (`/multi-ag-spec`)

Creado `specs/03-reproductor-de-clases-parallel.md` con el skill `multi-ag-spec`. **La spec original
no se ha tocado** (sigue en `Borrador`, 24 553 bytes). Los 38 criterios de aceptación se copiaron
verbatim y se verificó con `diff`: idénticos palabra por palabra.

**Hallazgo que define el reparto**: esta spec **no tiene backend, ni migraciones, ni instantánea de
EF**, así que los recursos de escritor único clásicos de este repo (carpeta `Migrations/`,
`AppDbContextModelSnapshot.cs`, `AppDbContext.cs`) no participan. El cuello de botella habitual
desaparece y el trabajo se puede partir en conjuntos de archivos disjuntos.

Reparto: **Fase 0 (contrato)** + **4 flujos** + **fase final de integración**.

| Flujo | Archivos | Duración |
| --- | --- | --- |
| A · Núcleo del reproductor | `player-position.ts` + `.test.ts`, `LessonPlayerPage.tsx` + `.test.tsx`, `App.tsx` | L (camino crítico) |
| B · Presentación de la actividad | `ActivityView.tsx` + `.test.tsx` | S |
| C · Entrada y estilos | `LessonsPage.tsx` + `.test.tsx`, `styles.css` | M |
| D · Documentación | `docs/lesson-player.md`, `README.md` | S |

Camino crítico: `Fase 0 → Flujo A → Integración`. El E2E (`e2e/lesson-player.spec.ts`) sale de los
flujos y vive en la integración, para no chocar de puerto con Playwright.

**Tres decisiones de reparto que merecen recordarse** (las tres documentadas y justificadas en el
plan, las tres vetables por el usuario):

1. **Stub en la Fase 0.** `LessonPlayerPage.tsx` (Flujo A) compone `ActivityView.tsx` (Flujo B). Sin
   resolverlo, A no compila hasta que B fusione y el paralelismo es ficción. Solución: la Fase 0 crea
   un stub de `ActivityView.tsx` con la firma congelada; A compila y se prueba contra él y B reemplaza
   el cuerpo. Es escritura doble pero **secuencial**, no concurrente.
2. **`App.tsx` va al Flujo A**, desviándose a propósito del catálogo de puntos calientes del playbook
   (que lo manda a integración). Razón: hay un solo escritor, la ruta pertenece a la funcionalidad y
   así el Flujo A no depende de ningún otro flujo.
3. **La frontera DOM/CSS se congela en la Fase 0.** `styles.css` lo escribe solo el Flujo C, pero A y
   B usan sus clases. Se congelan la lista de clases (`lesson-player-*`, `player-activity-*`), los
   `data-testid` del E2E y los textos literales («Actividad N de M», «Sin duración», «0 min»,
   «Duración incompleta»…). Sin eso, tres flujos y el E2E divergen en los mismos nombres.

Convención de nombres del repo confirmada: kebab-case con prefijo por área (`lesson-*`, `activity-*`);
`styles.css` tiene solo 99 líneas y las adiciones van al final.
