# 2026-09-29 — Diagnóstico y arreglo de `42P01: relation "Students" does not exist`

## Síntoma

Al guardar un estudiante en la app en marcha, tanto `GET /api/students` (`StudentReader.ListOwnedAsync`)
como `POST` (`StudentService.CreateAsync`) fallaban con
`Npgsql.PostgresException 42P01: relation "Students" does not exist`.

## Causa raíz

**No era un bug de código.** La entidad `Student`, `AppDbContext`, `StudentEndpoints`, la migración
`20260928212408_AddStudentsAndLessonAssignments` y el frontend estaban todos correctos y presentes. Lo que
faltaba era **aplicar la migración a la base de datos de desarrollo**.

`__EFMigrationsHistory` de `profefacilisimo` tenía solo 2 filas (`InitialCreate`,
`AddLessonSoftDelete`): le faltaban `AddCalculatedLessonDuration` y `AddStudentsAndLessonAssignments`.
De ahí que las tablas `Students` y `LessonAssignments` no existieran.

Contraste: `pf_integration` ya tenía las 4 migraciones aplicadas; `pf_e2e` tenía 3 (le faltaba la de
Students). Es decir, el fallo solo aparece al arrancar la API a mano contra la base de dev sin migrar.

## Arreglo aplicado

```bash
ConnectionStrings__Default='Host=localhost;Port=5432;Database="profefacilisimo";Username="profefacilisimo";Password="…"' \
Jwt__SigningKey='<SigningKey de .tools/local-settings.json>' ASPNETCORE_ENVIRONMENT=Development \
  ~/.dotnet/tools/dotnet-ef database update --project backend/Infrastructure --startup-project backend/Api --no-build
```

Resultado: creadas `Students` (con `CK_Student_Level`, `CK_Student_Name`, FK a `AspNetUsers` e índices
`IX_Students_UserId_DeletedAt` / `_UpdatedAt`) y `LessonAssignments` (índice único `(StudentId, LessonId)`).
Historial en 4 filas. `SELECT count(*) FROM "Students"` → 0, la tabla responde.

No se tocó ni una línea de código, ni entidad, ni migración, ni snapshot.

## Hallazgo operativo (nuevo)

- **Tres bases en el mismo contenedor con historiales independientes**: `profefacilisimo` (dev),
  `pf_integration`, `pf_e2e`. Migrar una no migra las otras.
- `scripts/Setup.ps1` y `scripts/Test-E2E.ps1` ya hacen `database update`; el desfase solo afecta a la
  base de dev cuando se arranca con `dotnet run`.
- `dotnet-ef` necesita **`Jwt__SigningKey` además de la cadena**, o el startup project no arranca.
- `dotnet-ef migrations list --connection '<otra cadena>'` sirve para verificar qué migraciones conoce el
  ensamblado sin tocar la base real (probado contra una base temporal y borrada después).
- `dotnet-ef` está en `~/.dotnet/tools/dotnet-ef.exe`.

## Pendiente (migración)

- Nada por commitear (arreglo solo de datos, no de repo).
- `pf_e2e` sigue sin `AddStudentsAndLessonAssignments`; `Test-E2E.ps1` lo aplica al arrancar.

# 2026-09-29 (segunda) — Filtro de búsqueda horizontal en «Mis estudiantes»

Petición de UI: el panel de filtros de estudiantes ocupaba mucho alto apilado en vertical; el usuario
quería una sola fila.

## Diagnóstico — la causa real (corrige mi primera hipótesis)

**Mi primera hipótesis era errónea.** Pensé que apilaba el `flex: 1 1 220px` de los `<div>` de campo, y
además que la página estaba limitada a 880px. Ninguna de las dos cosas era cierta:

- La sección `.students-page` **sí** mide 880px, pero lleva también la clase `.card`, que la limita a
  `min(100%, 470px)` — el `880px` nunca se usaba. Eso me llevó a probar un `.card.students-page` de
  900px, que **no arregló nada**.
- La causa real: **`.students-filters` nunca declaraba `flex-direction`**, así que heredaba
  `flex-direction: column` de la regla global de la línea 15:

  ```css
  form { display: flex; flex-direction: column; margin-top: 26px; }
  ```

  Con `column` + `flex-wrap: wrap` + `align-items: flex-end`, los cuatro hijos se apilan en vertical y
  cada uno se alinea a la derecha. Firma exacta en el navegador: contenedor de 822px de ancho y los
  hijos en `x = 826, 833, 947, 894`, todos en filas distintas. `.lesson-filters` sí declara
  `flex-direction: row`, y por eso la página de clases nunca mostró el problema.

## Cambio final (un fichero: `frontend/src/styles.css`, una propiedad)

```css
.students-filters { display: flex; flex-direction: row; flex-wrap: wrap; gap: 16px; align-items: flex-end; margin: 18px 0 22px; padding: 18px; background: #f1f5e6; border-radius: 12px; }
/* The fields share the row; the inner `column` keeps each label above its own control. */
.students-filters > div { display: flex; flex: 1 1 220px; flex-direction: column; gap: 6px; }
```

Descarté y revertí las dos pruebas especulativas (el `.card.students-page` de 900px y el
`min-width: 200px`): no eran necesarias. El diff final es **una sola propiedad** más un comentario.

- El `flex-direction: column` del `<div>` (etiqueta encima del control) se conserva: es intencionado.
- El `@media (max-width: 600px)` que apila en móvil **se dejó intacto** (decisión del usuario).
- `StudentsTrashPage.tsx` no tiene panel duplicado: es un envoltorio `<StudentsPage user={user} trash />`
  y el formulario está tras `{!trash && …}`.

## Trampa de verificación (importante)

Dos veces me fié de una **captura de pantalla obsoleta** y saqué conclusiones falsas: la misma imagen
vertical se releyó tras aplicar el arreglo, sugeriendo que el CSS no se aplicaba. Lo que lo resolvió
fue **medir en `page.evaluate`** (ancho computado + `getBoundingClientRect` de cada hijo), no mirar el
PNG. Lección: para verificar CSS en Playwright, medir geometría y estilos computados en la misma
ejecución; una captura puede ser de una corrida anterior aunque la ruta sea nueva.

  las dos pantallas se ven distintas.
